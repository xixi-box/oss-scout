# oss-scout

自动开源贡献流水线：每分钟发现 issue，机械粗筛后交给 OpenJev 细筛，由 OpenCode 或
Codex 在 GitHub Actions 修复、运行测试，再以账号持有者的身份提交 PR。
日常通过飞书查看扫描结果、候选队列、PR 记录，并修改模型与运行配置。

## 当前工作流

```text
Cloudflare Worker：每分钟扫描 57 个仓库（50 个正式＋7 个荣誉）
  → token 鉴权 → SQLite inbox 持久接收
  → 获取最新正文、完整评论、评论作者身份、关联 PR 和仓库规则
  → 机械粗筛 → OpenJev 细筛
  → 有额度且执行位空闲：先选今天最早可消费的暂存；没有则新候选直接开工
  → 需要等待：进入滚动暂存池，普通暂存默认最多 10 条（飞书可调）
  → Actions：OpenCode / Codex 自主搭环境、定位、修复并运行测试
  → Agent 自查调用链、边界、兼容性和测试覆盖，保存真实命令与结果
  → 发布前机械检查：最新 issue／仓库规则、额度、防重、交付范围及哈希
  → 核对交付文件及补丁哈希 → 账号身份与 DCO 签名 → 推送 fork → 开 PR
  → 同步飞书，持续同步 PR 状态与额度
```

所有日期、每日额度及凌晨 4 点均按北京时间计算。监控名单以
[configs/repositories.yaml](configs/repositories.yaml) 为准，当前维护 50 个正式＋8 个荣誉仓库；除 ClickHouse 仅跟踪存量 PR 外，其余 57 个每分钟扫描并按仓库规则贡献。荣誉身份不改变队列、额度和质量验证逻辑。

## 每日额度、暂存与消费顺序

- 每个北京时间自然日默认最多成功创建 **5 个新 PR**（飞书可调），按 GitHub 确认的创建时间记账。
  修复失败、重复 PR 不占新 PR 额度；发布结果不明时先对账。
- 新 issue 全天正常发现和消费，包括 **00:00–04:00**，不为特定时段预留配额、不额外限速；执行任务仍须原子预留名额。
- 今天可消费的合格候选优先，同日按原入队时间 FIFO；新到候选不能插到今天已等待的
  合格候选前面。取数或模型故障的重试退避仍有效。
- 普通暂存默认滚动保留 **最新 10 条**（飞书可调）。新 issue 粗筛、细筛都通过后入队；满池时清除最早
  的普通暂存，昨天、今天一视同仁。不合格的新 issue 不会挤掉已有候选。
- 执行中、已预留派发、已派发和待对账任务受保护；执行中与派发预留不占普通等待容量。
  飞书会区分「准备中」「等待运行」「执行中」「待对账」；远程取数失败显示「状态核查中」，不冒充普通暂存。Actions 真正开始后才显示「执行中」。各入口共用 SQLite 额度预留账本，同一候选由独立执行锁防止重复派发。
- 当天额度满后继续扫描、筛选并滚动更新暂存池，可消费时间顺延至次日 **04:00**。
- 每日 **04:00** 为当时已到期的历史暂存建立持久消费快照，按原入队顺序补位。
  批次可以在 4 点之后继续执行；今天可消费的候选仍优先。普通轮询不会额外捞取其他历史暂存。
- **当天创建的 PR 当天关闭**会释放一个额度，允许队列补位；旧日 PR 今天关闭不退今天额度，
  合并也不退额度。历史暂存还可由人工明确消费。

例如 A 正在执行且暂存已满：B 双筛通过后入队并清除最早普通暂存。A 完成后若还有额度，
优先执行今天最早可消费的候选；如果是 B，就先做 B。后来的 C、D 继续排队并滚动替换，
不会挤掉已经选中派发的 B。

## 串行执行与名额预留

剩余额度 R = 当日生效额度 − 已确认占用额度（当天关闭已释放的 PR 不再占用）。
R 为 0 时停止派发；R 大于 0 时，全局只允许 **1 个新 issue 修复任务**在途。
每日额度只决定当天还能创建多少 PR，不再决定并发数。准备、派发、执行和待对账均占用执行位。

每个任务在准备、筛选复查之前就通过 SQLite 原子预留一个名额；准备中、已派发和
发布结果待对账均计为在途。成功将预留转为实际占用，确认失败才释放，结果不明继续
保留预留并逐个对账。同一候选不能被多个入口重复预留或执行。恢复串行时只限制
新增任务，不取消已有任务；存量并行任务全部结束并对账后才派发下一个，跨日仍保留可能在新一天发布的任务预留。

## 粗筛、细筛与修复验证

**机械条件统一归粗筛**：issue 是否开放、指派与认领、重复标记、明确关联的修复 PR，
以及仓库的 CLA、授权等硬性要求。关键词命中只作为竞争 PR 的线索，明确修复同一个
issue 才拦截。完整评论和作者身份同时供后续 AI 判断。

认领与报告者自修意图同时识别中英文，忽略代码示例、引用及明确否定的声明。
未命中规则表示意图未知，细筛仍从完整正文和评论独立判断；报告者明确愿意自己提交
修复（包括条件式提议）应让位，不抢先自动开 PR。

粗筛通过后调用 OpenJev。刚筛完直接开工复用粗筛、细筛；同日短暂等待刷新粗筛、复用
细筛，正文或标题变化则重新核查；跨日、手动消费使用最新证据重新粗筛和细筛。
临时故障退避重试，正式淘汰与临时错误分别记录。持续通信故障在远程任务结束、确认未发布 PR 后回到暂存，按 5、10、20 分钟逐步退避，最长 60 分钟。一次重试授权只允许重开已中止的认领记录，成功发布与在途任务仍不可重开。

Codex 新任务使用 GitHub 环境 Secrets 的本地登录文件，不再领取服务器凭据或续租心跳。
CLI 心跳仅记录执行耗时；入队、遥测、审计及配置读取继续离开 HTTP 事件循环，避免磁盘等待阻塞控制器。
准备开工标记超过 60 秒后可检查回收：保护活跃线程、候选锁和账本预留；有派发 job ID 时，
必须完整查询并确认远程运行不存在才清理，远程运行存在或取数不完整时继续保留。

细筛读取完整贡献与安全规则，并结合中英文讨论和明确前置 PR 的当前状态，判断是否必须
私下披露、获得授权或等待依赖合并。引用关键词只用于补取事实，不直接淘汰；依赖已合并
不沿用旧等待结论。取数失败保留暂存重试。同日复用细筛也核对证据指纹；旧版结论或规则、
讨论、依赖状态变化会重新细筛，刚完成筛选的即时派发可复用。

修复工作流只准备通用工具。目标仓库的依赖由 Agent 在实际修复目录按需安装。
GitHub Actions 按目标仓库、运行环境和依赖清单复用 uv、pip、npm 包缓存。
诊断产物 `dependency-install.log` 记录缓存命中类型以及通过 PATH 调用的常见安装命令耗时与退出码。
`uv run` 计时包含它执行的命令。虚拟环境、node_modules 和源码构建产物各次任务单独生成。

OpenCode / Codex 自主选择环境、构建方式和测试命令，完成复现、最小修复、相关现有测试及
最终自查。Agent 负责检查真实入口、同类调用点、边界、兼容性、测试覆盖与最新中英文讨论，
如实记录执行命令、实际结果和未验证项；依赖、编译或命令错误不得冒充目标 bug 的复现。
系统不再独立复跑测试，也不再调用额外 AI 只读复审。Agent 成功完成后，由可信发布程序
通过机械检查自动创建 PR；Agent 本身没有 GitHub 写凭据。

两种工具共用完整补丁交付，源码、回归测试、Rust 内联测试和二进制 fixture 不再拆分。
报告明确标记 `verification_mode=agent`，测试结论来自 Agent 自测，不宣称独立验证。
正常实现最多 35 分钟，在 40 分钟总预算内最多追加一次 5 分钟，由同一 Agent 根据真实
日志补齐基本交付材料；不再要求固定 JUnit 格式、用例名称或输出片段才能通过外部验证器。
Agent 超时、CLI 失败或明确报告阻塞时停止发布，完整脱敏 CLI 输出、命令、退出码、耗时及
Agent 保存的测试日志留在诊断产物中，诊断与凭据不进入补丁。

发布前仍重新获取完整 issue、评论和关联 PR，执行关闭、指派、认领、重复、竞争 PR、
仓库规则、额度预留及防重等机械检查；取数不完整不当作没有限制。校验任务、base、交付
文件清单和实际补丁哈希，拒绝危险路径、构建垃圾及不允许的锁文件／CI 配置改动。
细筛仍按具体证据检查私下安全披露、前置依赖和不可获得的必要资源。

Hermes 已证实限制无写权限贡献者同时最多 **5 个开放 PR（含草稿）**，与每日 PR 额度不同。
粗筛和 Actions 开工前先检查，发布前再检查；满额时不继续花修复 token，不通过草稿或换账号绕过。

Agent 交付白名单单独保存 **30 天**，诊断日志保留 1 天。为兼容存量，控制器仍使用
`artifacts/verified-deliveries/<job_id>/` 路径和既有 artifact 名，保存原始补丁、结果、Agent
测试报告及哈希／来源清单，不包含 CLI 凭据或整个工作目录；路径名不表示做过独立验证。
明确发布限流或临时取数故障时，确认原运行已结束且未开 PR 后，可按退避规则暂存恢复。
恢复需要新的额度预留、查重、base／哈希核对和最新机械检查，不重新拆测试、复跑或 AI 复审；
base 已变化则重新修复。权限拒绝及发布结果不明不直接重发。
旧版明确限流记录可使用 `python scripts/retry_verified_publication.py --root /data --job <job_id>`
只读核对，显式加 `--apply` 仅授权后续正常流程，不直接发布，也不重跑旧 Actions。
历史已完成任务可以用只读归档工作流保存，不会重跑修复、推分支或创建 PR：

```powershell
gh workflow run archive-verified-delivery.yml --ref main -f source_run=<Actions运行ID>
```

**回归测试随源码完整交付**，包括 Rust 内联测试。报告记录文件清单和补丁
SHA-256；发布前核对任务、base、Agent 完成状态及实际暂存补丁，防止交付被替换。
构建垃圾不入补丁，锁文件与 CI 配置的改动退出自动发布。PR 描述使用真实根因、可复跑
测试命令。新任务由修复代理根据最终 diff 和仓库 PR 模板起草标题与正文，说明问题、
具体修复方式及相关兼容性；发布程序填入 Agent 报告的测试命令、结果及回归路径，明确来源，不捏造通过结论。
不再统一追加 AI assistance 或 oss-scout 宣传说明。缺少新文案的旧任务继续使用事实摘要。

发布提交统一通过 `commit_as_owner` 创建：作者、提交者和

## 飞书日常操作

| 位置 | 用途 |
| --- | --- |
| 扫描发现 | 粗筛、细筛各自记录结论；最终结果显示暂存、执行中、已开 PR 和链接，或具体淘汰、失败原因；含发现时间与更新时间 |
| 候选列表 | 只展示暂存、执行中；滚动挤出的候选移除，在扫描发现显示「已清除」及原因，保留原筛选结论 |
| PR 记录 | 查看 PR 当前状态、创建时间和源 issue 发现时间；关闭状态也回填扫描发现 |
| 仓库池 | 查看 50 个正式＋8 个荣誉仓库及参与状态 |
| 配置 | 在运行设置、OpenCode、Codex、Codiv 四行调整运行与模型配置 |

「配置」约 **5 秒**读取一次，校验通过后生效：

- **运行设置 → 修复工具**：切换 OpenCode / Codex，两套配置独立保留。
- **运行设置 → 候选池大小 / 每日 PR 额度**：填写正整数，默认 **10 / 5**。
  前者只限制暂存，执行中和已预留派发的任务受保护；调小后按原入队顺序清除最早普通暂存。
  后者按当天成功创建的 PR 计算，调大不会清空已用额度，并恢复今天因满额而等待的候选资格；
  调小不取消已执行任务，后续派发按新额度检查。非法输入显示在「应用状态」，保留上次有效值。
- **OpenCode**：模型、Base URL、API 密钥及思考强度。
- **Codex**：模型与思考强度，使用 ChatGPT 订阅登录。完整登录保存在 GitHub 的
  `codex-auth` 环境 Secret `CODEX_AUTH_JSON`，不写进飞书。修复任务使用私有本地凭据文件，
  CLI 自行刷新；可信步骤在任务结束（包括失败）后回写更新的登录，再释放会话。
  所有使用该账号的工作流共用 `codex-account-session` 串行锁，且只允许主分支使用环境凭据。
- **Codiv**：细筛模型、Base URL、API 密钥及思考预算。

按账号持有者授权，OpenCode / Codiv 密钥在飞书显示明文；公开日志与控制台查询接口
不返回密钥或 Codex 登录凭据。修改 OpenCode 密钥需服务器具备 Actions 仓库密钥管理权限。

飞书业务表在状态写入成功后立即触发差量同步。短时间内同表变化合并，只创建、更新或删除有变化的行。各表独立执行，慢查询不会挡住候选状态。普通失败按 5–60 秒退避重试，并保留待同步内容。跨进程或手动文件修改每秒检查，运行状态每 **10 秒**核对。

「PR 记录」每 **30 秒**通过 GitHub GraphQL 查询近期有变化的 PR，与上次完整快照合并，只写变化行。所有业务表每 **15 分钟**做一次全量对账。PR 取数遇到限流时，按 GitHub 返回的等待时间或额度重置时间重试，其他表继续同步。只有确认完整的空快照才可清理旧行。新 PR 尚未出现在列表时，从已确认发布账本补查具体 PR。
日常使用飞书，原前端看板已移除，`dashboard/` 保留控制器 API 与后台服务。

## PR 发布后的处理

PR 发布后由账号持有者手动处理评论、评审、CI 排错、追加提交和回复。系统只继续
同步 PR 状态、飞书记录和当天关闭释放额度，不再监听评论、分类评审、派发后续修复、
生成回复草稿或发送审批卡；旧卡片的推送和回复入口已移除。

历史文档、审计记录和旧任务不构成恢复自动跟进的授权。以后单独要求协助某个 PR 时，
只执行当次明确授权，不恢复后台自动机制。

## 日常检查与部署

```bash
# 测试系统自身
python -m pytest tests_v2 tests_dashboard -q

# 仓库指标、准入规则审计
python scripts/pool_rates.py
python scripts/pool_audit.py
python scripts/audit_ai_policy.py

# 只读运行诊断
gh workflow run diagnose.yml --ref main

# 主控制器部署
gh workflow run deploy.yml --ref main -f target_env=aliyun -f deploy_ref=main

# Worker 部署；修改 REPOS 后须重新部署 Worker
gh workflow run worker-deploy.yml --ref main
```

控制器镜像由 GitHub 托管 runner 构建并推送到 ACR。部署主机只拉取镜像、切换容器并验证运行状态。构建或推送失败时，在托管 runner 重试。

独立 bug hunter 支线在 Modal 执行，默认每日北京时间 04:00 触发；它与历史候选消费批次
是两件事，不自动把发现直接发布为新 issue。仓库是否适合自动贡献以最新规则和审计为准，
不把历史评分或门禁统计当作永久结论。

审计记录保存在 `state/worklog.jsonl`。队列 JSON 为兼容飞书与控制器保留，所有运行时
读改写通过 `queue_transaction` 跨线程、跨进程串行化。重启后的远程任务先核对再继续，
不重复派发可能仍在执行的写操作。更多约定见 [AGENTS.md](AGENTS.md)。

控制器性能诊断：慢队列事务记录 CPU、锁等待、持锁和提交耗时，`controller_slow_operation`
进一步区分读取解析、快照比较、原子落盘及表格构建。飞书本地文件与业务事件版本未变化时跳过整表构建，
仍检查远程执行状态并保留 15 分钟全量对账。临时故障回暂存后立即尝试派发其他已到期合格候选，失败项仍遵守退避。

准备失败时，在同一队列事务中清除本任务的派发和准备标记，持久化成功后才释放 SQLite 准备名额；写入失败保留账本占位。残留回收须拿到候选锁、核对账本，并完整确认远程任务不存在；已启动、归属变化或远程取数不完整时保持保护。
队列 JSON 使用流式 UTF-8 编码和复制备份，临时文件及落地文件均按 SHA-256 核对原始写入字节，保留 fsync 和原子替换，避免校验时再构造两份完整队列。慢日志细分编码、fsync、备份、替换和校验，并记录 RSS/swap；控制器限制 glibc 的堆 arena 数，减少多线程解析大 JSON 后的内存滞留。
